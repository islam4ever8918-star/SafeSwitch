SECURITY / ARCHITECTURE

Security from the packet up.

SafeSwitch is designed around a simple principle: critical network decisions should remain possible even when the systems surrounding them are under pressure.

SECURITY POSTURE

: OPERATIONAL

Remove the unnecessary trust.

Security isn't a single feature. It's the sum of the boundaries, dependencies, permissions and decisions that exist between an incoming packet and the system responsible for handling it.

Minimal Trust Surface

Reduce the number of external systems that must remain reachable for critical traffic decisions to continue.

Kernel-Level Enforcement

Where appropriate, packet processing can happen close to the network interface before traffic traverses higher layers of the stack.

No Runtime API Dependency

Critical data-plane behavior should not depend on a cloud dashboard or external API responding at exactly the moment a failure occurs.

Least Privilege

Keep permissions narrow, explicit and auditable across the components responsible for managing the system.

Observable by Design

Security-relevant behavior should be measurable, inspectable and correlated with the infrastructure events surrounding it.

Controlled Rollback

Changes to critical infrastructure should have a predictable path back to a known-good state.

Go deeper. Trust less.

The closer a system gets to the actual packet path, the more important its security boundaries become. SafeSwitch is designed around explicit layers rather than one enormous trusted application.

INTERNET UNTRUSTED

Traffic arrives from networks that SafeSwitch does not control and therefore treats as potentially hostile.

NETWORK INTERFACE EDGE

The NIC becomes the first meaningful observation point for traffic entering the host.

XDP EARLY PATH

XDP provides a location for extremely early packet processing before traffic travels through the normal networking path.

eBPF VERIFIED PROGRAMS

eBPF programs and maps provide programmable kernel behavior while remaining subject to the Linux kernel's verification and execution model.

APPLICATION LAST

Legitimate traffic eventually reaches the application layer, where application-level security controls continue to apply.

Stop bad traffic before it becomes work.

Security is an engineering discipline.

The strongest security claims are backed by boring, repeatable engineering processes.

04.01

Kernel Compatibility

Kernel-level software needs explicit compatibility testing across supported kernels, distributions and deployment environments.

04.02

eBPF Verification

eBPF programs operate within the Linux kernel's verification and execution model. Program behavior, map access and lifecycle should remain tightly controlled.

04.03

Dependency Discipline

Dependencies should be inventoried, reviewed and continuously evaluated for known vulnerabilities and unnecessary exposure.

04.04

Reproducible Operations

Critical configuration and infrastructure changes should be versioned, reviewable and capable of being rolled back to a known-good state.

Change the system without losing control.
